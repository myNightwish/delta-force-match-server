# 核心匹配可靠性复核

日期：2026-10-23

## 结论与范围

当前 V4 双人匹配的条件判断、并发占位和双人确认，在本次检查中没有发现条件穿透或重复组队问题，适合小规模真实用户试运行。不能据此保证实际玩家水平相近、全局组队数量最多或线上高并发容量。

本次仅新增回归测试和审计记录，没有调整线上匹配规则或修改生产数据。所有验证均使用本地临时数据库，未对 Render 做压力测试。

## 已验证

- 实力范围、打法范围、装备门槛均为双向约束，边界值包含在允许范围内
- 区服、平台、语言、语音方式、开局时段和目标按既定规则匹配，地图及难度必须有交集，任务局必须有共同任务
- 发布时由服务端重新计算总分，不信任传入的总分，手填模式及缺少原始指标被拒绝
- 手动申请与自动匹配均经预留逻辑再次核验，不只依赖大厅之前展示的结果
- 离线、过期、不同模拟池、近期排除的候选不可预留，匹配名额原子占用
- 超时与婉拒释放名额，保留原排队时间；双方确认后才成为就绪队伍；携带旧队伍 ID 的确认不能确认新队伍
- 约定的共同地图和任务有固定排序，调换双方或地图顺序不会改变有效约定

完整后端测试：147 项通过。新增 6 项审计测试包括 5,000 组固定随机种子条件组合的独立规则校验及正反方向验证、边界和零分、16 人并发抢同一候选、24 人并发自动发布形成 12 个互不重叠队伍、10 轮申请与取消竞态、16 次并发重复确认。新测试位于 tests/test_matching_reliability.py。

## 待优化项

### P2：当前采用局部最近分数优先，不能保证更多人组成队伍，也不能保证等待公平

位置：app/services/pilot.py 的 _auto，约 220–239 行。

先按分差排序，再以创建时间排序。已经构造并复现四人例子：可匹配边为 A–C、A–D、B–C。按 A、B、C、D 到达，C 先选择分数更接近的 A，最终只有一队、两人在等；实际上 A–D 和 B–C 能组成两队。这不是条件穿透，而是局部贪心策略的效率局限。持续有更近分数的新用户到达时，长等待者也可能持续靠后。

建议：先明确“等待时间”和“分差”的业务优先级，引入有限的等待时间加权；候选池较大后可考虑短窗口批量匹配。不要自动放宽用户硬条件，也不要拆散已经预留或确认的队伍。当前没有擅自改变这些产品取舍。

### P2：候选扫描逐人查询，所有业务事务使用 BEGIN IMMEDIATE

位置：app/services/pilot.py 的 db、_auto、candidates。

候选检索扫描所有等待者，对每人额外查询模拟池、在线状态和排除记录，然后排序分页。即使只显示 6 张卡片，也仍遍历整个池。读取候选时还会更新在线与过期状态，因此同样持有写事务。并发正确性得到了保护，但高频轮询会竞争写锁。

本机临时数据库、全部候选兼容且在线、单请求、每组 5 次的中位数：

| 等待候选 | 候选首页耗时 | SQL 语句数 |
|---|---:|---:|
| 100 | 3.12 ms | 308 |
| 500 | 13.50 ms | 1,508 |
| 2,000 | 53.62 ms | 6,008 |

这些数据不包含网络、HTTP 鉴权和限流开销，不能作为 Render 容量承诺。建议把模拟池、在线状态和排除记录批量获取，在 SQL 先做基本条件筛选，减少 JSON 反复解析及事务持锁时间；更大规模时再评估数据库和匹配任务架构。

### P2：分数计算正确不等于原始数据真实，也不等于模型效果已验证

三个指标仍由玩家填写，服务端重算只能防止直接篡改总分，不能阻止虚报 KD 和战斗分。没有真实对局样本证明当前综合分及默认范围能稳定预测合作体验。计算口径移到服务端能避免前端直接读取公式，但不能保证不能通过输入输出推断。

建议：先小范围收集确认率、实际游玩率、双方水平相符反馈、等待时长和复用率；区分“条件不匹配”和“数据虚报”，有证据后再调整分数与范围，必要时增加资料核验。

## 建议顺序

1. 保持目前的双向硬条件与原子预留保护
2. 优先消除逐人 SQL 查询，补对应性能回归，再用接近部署环境的负载验证容量
3. 明确等待公平性与分差的优先级后调整候选排序
4. 小范围真实用户试运行，用实际反馈验证分数模型，不宣称已验证玩家真实水平


## 2026-10-23 后续优化

已完成候选查询批量化：将在线状态、模拟池隔离和排除记录合并进一次 SQL，自动匹配也只解析每个候选资料一次。保留 `_reserve` 中的独立校验及原子事务，不改变硬条件、分差优先策略或已预留队伍。

相同本机临时数据库场景、每组五次中位数：100 人 1.84 ms / 8 条 SQL，500 人 7.56 ms / 8 条 SQL，2,000 人 31.48 ms / 8 条 SQL。此前对应值为 3.12 ms / 308、13.50 ms / 1,508、53.62 ms / 6,008。该测试仅比较本地检索开销，仍不代表线上容量；全池扫描与写事务串行限制依然存在。

新增候选筛选与原在线／排除／模拟池策略一致性测试，以及 SQL 次数不随候选人数逐人增加的回归测试。等待公平性及更高组队数量的策略仍待明确业务取舍后实施；本阶段继续使用社区自报指标，不增加未经验证的自动资料核验。
