# 安全检查与三人组队改造评估

检查日期：2026-10-23

范围：当前本地源代码、HTTP 集成测试、公开依赖公告检查；没有进行线上渗透、DDoS 模拟、Render 权限检查或主机审计

## 本次补强

- JSON 请求体在解析前限制 64 KiB，语音 multipart 请求整体限制约 1.15 MB，分块传输同样检查
- 增加主要状态/候选/消息读取限流，分享读取、增长操作和运营接口分别限流
- 新运营接口无论开发还是生产都要求至少 32 字符服务端密钥，默认拒绝
- 分享代码与身份凭证分离，分享只返回字段允许列表，所有邀请仍重新检查双向兼容和名额
- 预约写入使用原子事务，不能通过取消别人的预约释放其名额
- API 返回 no-store、nosniff、no-referrer，保留已有语音私有缓存设置
- 生产关闭 API 文档入口，禁止开启旧版演示 API
- 前端只注册当前产品页面，不再发布旧登录/支付等演示路由
- 正式一键启动脚本改为本机监听、统一端口，避免旧脚本的 0.0.0.0 与代理端口不一致
- 旧 Compose 曾映射默认密码 PostgreSQL 与无密码 Redis 到主机公网接口，并未持久化实际 SQLite。已替换为仅本机暴露 API 的单服务配置和 SQLite 命名卷，旧卷不删除。本次未实际执行 Docker 构建或启动验证
- 生产依赖收敛到当前匹配 API 的六个直接依赖，固定已测试版本；旧 python-jose 和 ecdsa 不再纳入生产安装

## 当前评估

### 身份与越权

队伍聊天和语音按成员关系校验，未确认不能聊天；已有测试覆盖陌生身份访问

当前未发现将公开分享代码当作登录凭证、直接 SQL 拼接用户输入或当前页面 v-html 注入的路径，这不是“保证没有漏洞”

匿名身份使用浏览器内长期 Bearer 凭证，XSS、恶意扩展或设备被他人访问时可能失窃。缺少匿名会话到期、设备管理、全局撤销；未来收费和正式手机号账户上线前需要把用户标识与可撤销会话凭证分开，核对账户合并后的旧匿名凭证是否应失效

### 滥用与可用性

现有限流按地址及身份实现，但无法单独阻止代理池刷号、分布式攻击或恶意占位。对公网扩大推广前应增加入口层防护、告警、封禁/举报能力，并在异常流量时按风险启用人机验证

SQLite 事务可以保证当前单实例的原子名额操作，但读取中仍有写事务，候选筛选仍有逐条检查。没有完成并发容量或慢请求压力测试，不承诺承载人数

IP 使用 ASGI 客户端地址；实际 Render 代理转发链、可信代理配置与限流误伤需要在部署环境验证，不能盲目信任客户端自带 X-Forwarded-For

### 数据与部署

已确认本地 .env 和 pilot.db 被 Git 忽略，未被跟踪

线上是否实际挂载 /var/data 持久盘、是否有备份及恢复演练、Render/GitHub 账户是否启用 MFA 未验证

聊天语音有七天保留限制，但参与者、招募、预约、访问统计暂无完整自动删除策略，需制定保留和注销规则

新运营密钥不写浏览器持久存储，但仍是单一管理密钥，没有管理员分级、密钥轮换审计与操作日志，适合少量内部运营

### 依赖审计

npm audit 针对现有前端锁文件报告 41 个受影响依赖节点：28 high、6 moderate、7 low，0 critical。这是依赖传播节点数量，不等同于 41 个可远程利用的产品漏洞

涉及 Vite/esbuild 开发服务器、PostCSS/ZIP 等构建链、Vue SSR 与国际化依赖。当前线上是静态 H5，不提供 Vite 开发服务和 Vue SSR，也不允许用户上传构建用 ZIP/CSS 或翻译包，降低相应路径的直接暴露，但不能据此宣布已修复

**前端依赖风险尚未清零**：uni-app alpha 依赖链需单独评估兼容升级，禁止直接 npm audit fix --force。公网推广前应完成兼容升级/替代与复测，并在主机层避免把开发服务器暴露到公网

后端原审计发现 python-jose 与 ecdsa 的两类公告，均由旧演示鉴权依赖引入，当前匹配/手机号流程使用随机会话与 HMAC，不使用该 JWT 链；本次已从生产依赖移除，正式后端环境也卸载这两个包。整改后正式 Python 3.14 环境扫描 41 个已安装包，未发现已知公告。后续应使用实际运行环境定期重扫，零已知公告不等于零漏洞

## 扩充三人组队

改造量：中到较大，主要集中在组局内核与组队界面，不需重写资料表单、短信登录、预约或全部前端

当前限制不是一个人数常量：squads 存 a/b 两个 ticket ID，确认数等于 2，聊天鉴权、历史查询、释放名额、反馈完成和模拟器都显式处理两人

建议结构：

1. squads 保留队伍级状态，新增 squad_members（ticket_id、角色席位、确认状态）
2. recruitment_slots 独立存每个待招募席位的要求，允许一或两个席位不同条件
3. 人员自身配置单独保存，每个候选满足被分配席位，候选自己的队友要求也需明确适用于谁
4. 队友席位不能被同一身份重复占用，活跃招募不能同时参加多个队伍
5. 地图/难度与任务检查整队交集；不能只检查 A-B、A-C、B-C，因为三组各有交集也可能没有共同交集
6. 同一数据库事务完成三个成员的名额保留、状态检查和占位，防止同时被不同队伍抢走
7. 约定 2/3 已确认时的等待、拒绝和超时规则，是释放一席还是解散整队；任何新成员加入后重新检查整队条件
8. 聊天、历史、反馈、队伍人数展示和测试模拟器迁移为成员集合，旧两人队伍也兼容

第一版三人建议先支持一位发起者公开两个席位、逐席加入；整队满足条件后统一确认。先不做全池任意三人组合的最优分配

无需 AI 判断。确定性规则可以检查合法性；排序和搜索使用候选限制与小范围组合。候选几十人时组合枚举本身通常可控，真实耗时还取决于数据库、过滤和同时争抢，需压测后给出容量结论

新增分享仅引用 ticket，不把 a/b 结构暴露到公开链接；预约与四项统计独立封装，便于后续成员表改造。但统计中的双方确认判断需要随人数升级为全员确认
